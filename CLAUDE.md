# CLAUDE.md

Guidance for Claude Code (claude.ai/code) working in this repository.

## Project overview

SensoresIoT is an IoT sensor-monitoring platform: ESP32 boards running Arduino firmware POST readings to a FastAPI backend that stores them in TimescaleDB (Postgres). Three parts: `backend/` (FastAPI + Postgres/Timescale), `esp/` (Arduino/C++ firmware) and `frontend/` (React client app).

## Commands

### Backend (from `backend/`)
- Run: `uvicorn main:app --reload --host 0.0.0.0 --port 8000` (needs `venv` activated and a reachable DB). Deps: `pip install -r requirements.txt`. No tests or linter configured.

### Full stack via Docker
- `docker compose up` from the repo root brings up `timescaledb` + `api`. `docker-compose.yml` is the production-like base; `docker-compose.override.yml` is auto-merged in dev (Postgres on host `5433`, `./backend` bind-mounted, uvicorn `--reload`).
- Needs a root `.env` (see `.env.example`): `POSTGRES_PASSWORD`, `CORS_ORIGINS`, `RESEND_API_KEY`, `FRONTEND_URL`, `JWT_SECRET_KEY`.
- `db/init.sql` runs only on first container creation. To re-apply schema changes: drop the `postgres_data` volume or run the SQL by hand.

## Backend architecture

Layered, one module per entity, wired in `main.py`:

```
routers/      -> endpoints, request/response wiring, auth dependencies, rate limits
services/     -> business logic, authorization, orchestrates repos inside one transaction
repositories/ -> raw SQL (psycopg2), cursor as first arg, no business logic
schemas/      -> Pydantic request/response models
core/         -> config, security (JWT/hashing), deps, limiter, email
```

- Every service function opens its own `with get_connection() as conn: with conn.cursor(...) as cur:` (see `db.py`); the context manager commits on success and rolls back on exception. Multi-step operations share one cursor/transaction — never split across connections.
- Repos never raise `HTTPException` and never check permissions; services own both (`raise HTTPException(status, "mensaje")`).
- Naming and messages are in Spanish (`usuario`, `dispositivo`, `medicion`, `crear_`, `obtener_`, `buscar_`) — keep new code consistent.
- **Authorization lives in the service layer only**, resolved by `dispositivo_service.rol_en_dispositivo(cur, dispositivo_id, usuario_id, rol)` -> `'admin' | 'owner' | 'editor' | 'viewer' | None`, through three wrappers: `validar_acceso_al_dispositivo` (any role), `validar_edicion_en_dispositivo` (`ROLES_EDICION` = owner/editor) and `validar_owner_en_dispositivo` (`ROLES_OWNER`). All resolve the device first, so a missing device is 404 and a forbidden one 403. Never query `usuario_dispositivo` yourself.

### Auth model
Two credential systems (`core/security.py` / `core/deps.py`):
- **Users**: bcrypt hash + JWT access token (`ACCESS_TOKEN_EXPIRE_MINUTES = 30`, in the response body) + refresh token (`REFRESH_TOKEN_EXPIRE_DAYS = 7`) in an `httponly`/`secure`/`samesite=strict` cookie, persisted hashed in `refresh_token`. Gated by `get_usuario_actual` / `get_usuario_admin`.
- **Devices**: per-device secret, only its SHA-256 stored as `dispositivos.secret_hash`; sent as `Authorization: Bearer <secret>` + `X-Dispositivo-Id`, compared with `hmac.compare_digest` in `get_dispositivo_autenticado`.
- **Secret rotation is device-initiated** (`POST /dispositivos/rotate-secret`): the board authenticates with its current secret and gets a new one back once. Two secrets stay valid during a rotation (`secret_hash` + `secret_hash_anterior`); the old one is cleared the first time the device authenticates with the new one (implicit commit). Invalidating it immediately would brick a device that never received the response. An admin forces a rotation with `POST /dispositivos/{id}/marcar-rotacion` (raises `rotacion_pendiente`), which rides back as `rotar_secret` in the `POST /mediciones/` response. `POST /dispositivos/{id}/regenerate-secret` requires reflashing -> bench/factory only.
- Rate limiting: `slowapi` per-IP, applied per-route with `@limiter.limit(...)` on login, register, resend-verify and device vinculation.

### Time-series data (`mediciones`)
- `mediciones` is a hypertable (`time`/`sensor_id`/`value`) with two continuous aggregates (`mediciones_por_hora`, `mediciones_por_dia`), all defined in `db/init.sql`. Retention: raw 90 days, hourly 1 year, daily forever.
- **Tiered query strategy** (`medicion_repo.FUENTES`, finest to coarsest): for a requested range, pick the cheapest table that still meets the resolution *and* still retains data that far back, falling back to a coarser one rather than returning nothing. `resolucion_grafico` is the single point of choice — it returns `(fuente, bucket)` and both `buscar_puntos` (chart) and `buscar_resumen` (single stat) receive that same pair, which is what makes them incapable of disagreeing.
- `bucket` is `None` when the sensor's real reading count for the range fits under `TOPE_CRUDO` (1000): raw readings go back unaggregated, since a bucket finer than the device's sampling interval only creates empty slots and a coarser one throws away real resolution. Above the cap the target is ~200 buckets (`TARGET_PUNTO`), floored at `plan_service.intervalo_efectivo_seg` rather than a fixed 30s. Read the comments in that file before changing the selection logic.
- `medicion_service.crear_medicion` enforces a minimum interval per sensor and echoes it as `intervalo_sugerido` so firmware throttles itself. The minimum is `max(dispositivos.intervalo_configurado_seg, plan_floor)` (`_obtener_intervalo_minimo`); `intervalo_configurado_seg` arrives for free in `get_dispositivo_autenticado`'s `SELECT *`. Invalid sensor ids, out-of-range timestamps and too-soon readings are reported in the response, not as HTTP errors — never fail the whole batch.
- **Readings arrive late and out of band.** The firmware buffers what it could not send and flushes it with each reading's original `time`, so one batch can hold hours of points per sensor. Consequences: each candidate is checked against its real *neighbours* (`medicion_repo.mediciones_en_ventana`, not the sensor's latest row); an already-existing timestamp is `duplicadas`, not an interval violation; the whole batch goes in with one `execute_values` + `ON CONFLICT DO NOTHING`; `last_seen_at` is `now()`, never the reading's time, or a flush of old data would mark a device that just reported as stale.
- The `(sensor_id, time)` unique index is what makes retries safe: the board re-sends any chunk it did not get a 2xx for, including ones that were inserted but whose response was lost.
- The CAGG policies use a much wider `start_offset` (3 d / 30 d) than their `schedule_interval` on purpose: a backfilled row outside that window is marked invalidated but never re-materialized, so it would vanish from any chart served from an aggregate. **The window must stay above the firmware's maximum buffer horizon.**

### Planes y suscripciones
- `planes` is a small fixed catalog (`free`, `premium`). Its `id` is `TEXT`: `'free'` is referenced as a stable literal (the fail-closed fallback) and a numeric id breaks on any reseed. `NULL` means *unlimited* in `dispositivos_incluidos`, `retencion_dias` and `max_alertas`.
- **A subscription is current on dates alone**: `inicio_at <= now() AND (fin_at IS NULL OR fin_at > now())`. `estado` (`activa`/`cancelada`/`revocada`) records intent and **never** enters that predicate — cancelling does not touch `fin_at`, so "cancelled on day 3 but paid through day 30" needs no special case. There is no `vencida`: expiry is derived, so no job can leave the state lying about the dates.
- **Free is the absence of a current subscription**, not a row: nothing is inserted on signup.
- `suscripciones` carries `EXCLUDE USING gist (usuario_id WITH =, tstzrange(inicio_at, fin_at) WITH &&)` (hence `btree_gist`): the service's 409 is a check-then-act two concurrent requests can both pass, and two current subscriptions mean revoking one would not downgrade the user. `tstzrange` is half-open `[)`, so revoking with `fin_at = now()` and reassigning with `inicio_at = now()` do not collide.
- **`services/plan_service.py` is the single point of truth for limits.** Every gate reads `limites_de_usuario`, `limites_de_dispositivo`, `limites_de_dispositivos` (batch, one query for the whole panel) or `ventana_de_consulta`; nothing else touches `planes`/`suscripciones`. They take a cursor because gates run inside already-open transactions, and they return the `planes` row as-is, so adding a catalog column needs no service change.
- Which helper: **anything about a device comes from the plan of the device's *owner*** — retention, sampling interval and alerts (a free user with shared access gets exactly what the owner has). Only **account limits** (sharing one's own devices, i.e. creating invitations) read the requesting user's own plan.
- Fail-closed means *indeterminate data*, not swallowed errors: no current subscription or a missing catalog row yields free (`LIMITES_FREE` is the hard floor). Do not wrap these in `try/except` to return free on a psycopg2 error — after an error the transaction is aborted and every later query on that cursor fails anyway.
- Downgrades only ever stop reading more; nothing is deleted. Revoking sets `fin_at = now()` and keeps the row.

**Enforced gates.** Three catalog columns have a consumer today: `retencion_dias`, `intervalo_minimo_seg` and `puede_alertas`/`max_alertas` (see "Alertas"); the rest are catalog-only. **Export is not a gate**: `puede_exportar` is `true` for both plans (`db/migrations/005_export_habilitado.sql`) and stays as a lever for something narrower later.
- **`retencion_dias` — query clamp.** `plan_service.ventana_de_consulta(cur, dispositivo_id, rol)` turns it into a `piso` (oldest queryable instant, `None` = unlimited), applied in `sensor_service.obtener_grafico` / `obtener_historial` and in the export. It **raises `desde`, it never errors**: the graph response carries `desde_efectivo` / `recortado` / `retencion_dias` so the frontend can render what it got and offer the upgrade, and a range entirely outside the window returns empty instead of a 400. For `/historial` the piso goes down to `medicion_repo.buscar_historial` as a lower bound, ending pagination on its own.
  - Raising `desde` only *lowers* the range's age, so `_elegir_fuente` picks an equal-or-finer source — the tiered strategy can never be starved by the clamp.
  - **Admins are exempt** (`rol == "admin"` short-circuits before any query): support has to see what a customer reports from weeks ago. It is a commercial limit, not access control.
- **`intervalo_minimo_seg` — write gate, floor only.** `_obtener_intervalo_minimo` computes `max(intervalo_configurado_seg, plan_floor)` at request time, never stored pre-clamped, so a downgrade never overwrites the owner's chosen value — the owner can ask for a *slower* interval (battery/buffer autonomy) via `PATCH /dispositivos/{id}/intervalo` and keep it. `dispositivo_service.configurar_intervalo` rejects (400) a value below the *current* floor or above the 24 h sanity cap; `intervalo_seg: null` resets to automatic.
  - `crear_medicion` opens a **second, dict cursor on the same connection** just to read the plan: its main cursor yields tuples because `sensor_repo.ids_por_dispositivo` and `medicion_repo.mediciones_en_ventana` unpack positionally.
- **Writes are never clamped by retention.** `ANTIGUEDAD_MAXIMA` (90 days) tracks the raw retention policy, not the plan: a free user writes just as deep as a premium one and merely sees less, so the full history is already there the day they upgrade.

### Export (`GET /dispositivos/{id}/exportar`)
Streams a device's history as one CSV — all its sensors pivoted into columns on a shared time axis, not one row per sensor reading. `services/exportacion_service.py` is the only consumer of this pattern; read it before adding a second streaming endpoint.
- Available to every plan; the only limit is `ventana_de_consulta`, applied exactly like `obtener_grafico`. A fully-clamped range is not special-cased: `desde >= hasta` just matches zero rows, so the response is a 200 with a header-only CSV.
- **Both range and resolution default to "everything".** With no `desde`, the range starts at `medicion_repo.inicio_historial`, which takes the `LEAST` of `min()` from `mediciones_por_dia` *and* raw: raw only holds 90 days so the daily aggregate knows the real start of history, but a device installed hours ago has nothing materialized there yet (the policy runs every 3 h). `LEAST` ignores NULLs, which is what lets one query serve both.
- **The default never downsamples.** With no `intervalo_seg`, `medicion_repo.iterar_pivot` groups by the source's time column as-is (`GROUP BY time` on raw): one row per distinct stored timestamp, nothing averaged. Bucketing by `intervalo_configurado_seg` would be wrong — that is today's config, not a property of the stored data, so a device that recorded every 15 s last month and sits at 45 s now must still export all of last month's points. The `avg()` there is a passthrough (the unique index guarantees one row per sensor per instant), present only so the `FILTER` pivot type-checks.
- **`intervalo_seg` is opt-in aggregation and it flips the source-selection rule.** `medicion_repo.fuente_para_export(desde, intervalo_seg)` returns `(fuente, bucket)` via two strategies: without an interval it walks `FUENTES` finest-first (max fidelity, degrading only when retention forces it), which is *inverted* from `_elegir_fuente` (coarsest table meeting a ~200-point visual budget); with an interval the caller already accepted an aggregate, so `_elegir_fuente` is the right helper — 1 h over two months comes from the hourly CAGG (~1.4k rows) instead of scanning hundreds of thousands of raw rows. Do not collapse these paths, the goals genuinely conflict.
- **Aggregating changes the CSV's shape** (three columns per sensor — prom/min/max — instead of one), so `medicion_repo.export_con_stats(fuente, bucket)` is the single predicate for it and both repo and service ask it rather than re-deriving. It is true whenever the source is pre-aggregated *or* an interval was requested. A requested interval finer than the surviving source is clamped up to its native granularity (60 s over 200 days becomes 1 h), which is why `X-Intervalo-Seg` reports the *effective* bucket and `X-Fuente` the table.
- **`GROUP BY 1`, not `GROUP BY bucket`.** On the aggregate tables the time column is already named `bucket`, and Postgres resolves an ambiguous `GROUP BY` name against the input column, silently ignoring the requested interval.
- **Pivoting is per-instant, so a straddled loop pass costs a row, not data.** `leerYBufferizar()` stamps each sensor separately (whole seconds), so sensors in one pass usually share a timestamp but can land 1 s apart, emitting two half-filled rows. Accepted trade: alignment is cosmetic, completeness is not.
- **Two-phase execution, because the connection has to outlive the endpoint function.** A `StreamingResponse` generator is consumed after the handler returns, so `preparar_export_dispositivo` does validation (404/403/400, plan clamp, sensor list) in a short-lived `get_cursor()` — **every possible `HTTPException` has to be raised there** — and returns a generator that opens its own connection via `db.get_cursor_streaming` once Starlette starts iterating. **Never raise `HTTPException` inside that generator**: the 200 is already streaming, so an error there can only truncate the download.
- `get_cursor_streaming` (named/server-side psycopg2 cursor, the only one in the codebase) exists so a multi-hundred-thousand-row export does not `fetchall()` into RAM. Reach for it for any future endpoint streaming a large ad-hoc result.
- `main.py` exposes `Content-Disposition` and the `X-*` export headers in its CORS `expose_headers` — without that a browser `fetch` cannot read the filename or the clamp metadata, and a plain `<a href>` cannot carry the JWT.

### Alertas (Tier 4.3)
Threshold rules on a single sensor (`mayor`/`menor` + `histeresis`), evaluated inline in `crear_medicion` right after `insertar_muchas`, in the same transaction — no worker. `services/alerta_service.py` owns the state machine, `repositories/alerta_repo.py` is plain SQL.
- **An alert belongs to the device, not to whoever created it.** `alertas.creado_por` is informational (`ON DELETE SET NULL`) and plays no part in authorization or in who gets notified. Everything is looked up through the device: `GET /dispositivos/{id}/alertas`, `GET /dispositivos/{id}/alertas/eventos`, plus `GET /alertas/eventos` as a global log across every device the user can reach.
- Authorization is the `validar_*` trio: owner/editor create, edit and delete; viewer only reads.
- **Gated by `puede_alertas` from the *device owner's* plan** (`limites_de_dispositivo`), not the creator's: an editor on free can create alerts on a premium owner's device, same as they already see that device's full history. `max_alertas` is counted **per device** (`alerta_repo.contar_por_dispositivo`), so a premium device has no ceiling on rules per sensor either.
- **`tipos_sensor` carries no physical range** (`valor_min`/`valor_max` dropped in migration 008): an `umbral` is accepted as given, with no server-side plausibility check.
- **The rule's state (`normal`/`disparada`) is persisted on `alertas`, not derived**: each request only sees the values in its own batch, so without stored state there is no way to tell "just crossed" from "was already over". Histeresis is the return leg — `mayor` needs `valor < umbral - histeresis` to go back to `normal`, so a value oscillating at the threshold does not flap and spam.
- **`ultima_evaluacion_at` is the `time` of the last reading evaluated, not `now()`.** A reading `<= ultima_evaluacion_at` is skipped outright, so a resent chunk never re-fires a transition and an out-of-order batch cannot walk the state machine backwards.
- **Late data (a buffer flush) is evaluated, not skipped** — the alternative silently drops a real threshold crossing. Every transition is written to `alerta_eventos` with `tardio = true` when its reading is more than `FRESCURA` (5 min) older than server time, but **only the batch's last transition per rule is emailed**: a 12 h flush that oscillates 50 times sends one mail; the rest stay as history with `destinatarios`/`notificados` at 0.
- **Recovery (disparada to normal) notifies too** — a `disparada`-only alert leaves the user checking the app to find out if it resolved.
- **Every user with access to the device is a recipient by default, and muting is per *device*, not per rule** — nobody wants the "temp > 30" mail but not the "temp < 5" one from the same box. The preference is `usuario_dispositivo.notificar` (`DEFAULT true`), so `alerta_repo.destinatarios_de_alerta` is a plain `JOIN usuario_dispositivo ud ... WHERE ud.notificar`: that table *is* the definition of "everyone with access to this device", which is exactly the recipient set (migration 009 dropped `alerta_preferencias`). `PUT /dispositivos/{id}/notificaciones` (any role, viewer included) is the only writer, and the `UPDATE` scoped to `(dispositivo_id, usuario_id)` *is* the authorization — no link, no rows affected, 404.
- One `alerta_eventos` row can have several recipients, so instead of a boolean: `evaluar_batch` stamps `destinatarios` on the transition it will email, and `notificar_eventos` fills `notificados` after actually sending, with try/except per address so one bounce does not block the rest or the count.
- **Email goes out via `BackgroundTasks`, after the response** — `resend.Emails.send` is blocking HTTP and the ESP32 that just POSTed cannot wait on it. `routers/mediciones.py` schedules `notificar_eventos` only when `crear_medicion` returned notifications, same fire-and-log pattern as the verification email (`try/except` + `print`, never raises).

### Compartir dispositivos: invitaciones (Tier 4.4)
Two shapes in one table (`invitacion_dispositivo`), told apart by `email IS NULL`: a **global link** (7 days, unlimited uses, at most one per role per device) and a **directed invitation** (30 days, single-use, no cap on how many are outstanding). `dispositivo_service` owns both; `invitacion_dispositivo_repo` is plain SQL.
- **The token is stored in plaintext, deliberately — do not "fix" it into a hash.** A share link is not a credential like `refresh_token` or `secret_hash`; it is a capability the owner must be able to re-read, re-copy and rotate (`GET /dispositivos/{id}/invitaciones` returns it), and hashing would buy nothing: the same dump that leaks the row already holds the readings it grants access to. The consequence is that the weak point moved to anything that logs URLs, which is why the token travels in the request body in both accept and revoke.
- **`idx_un_solo_link_por_rol` is partial (`WHERE email IS NULL`)** — without the predicate it would cap directed invitations at one per role too. The index cannot know about expiry, so `invitacion_dispositivo_repo.crear` handles it in the `INSERT`: `ON CONFLICT ... DO UPDATE ... WHERE expires_at <= now()` overwrites an expired link in place and leaves a live one untouched, returning nothing, which the service turns into the 409. That is why the conflict is resolved by a returned row instead of catching `UniqueViolation`, and why a fresh link keeps the row's `id` (only `created_at` resets).
- **Every repo query is scoped by `dispositivo_id`, including the ones addressed by `id`** — the router validates ownership against the path's device, so a bare-`id` lookup or delete would let the owner of one device act on another's invitation. The scoped pair *is* the authorization.
- **Creating reads the inviter's own plan, accepting reads the owner's**: sharing your own devices is an account limit, while accepting has no requesting-user plan to speak of and has to ask whether *this device* may be shared at all. Re-checking on accept is what kills links already out in the wild after a downgrade.
- **Accepting requires no prior access — the token is the authorization**, so `aceptar_invitacion` is the one path here without a `validar_*`. Create, list, regenerate and revoke are `ROLES_OWNER`: an editor can use a device but cannot hand it out.
- **Role is never upgraded by accepting**: a second acceptance hits the `usuario_dispositivo` primary key and comes back as 409 "ya tenés acceso"; a viewer who later uses the editor link stays a viewer and the owner changes the role from `/accesos`.
- **Only the directed invitation is consumed on use** (deleted in the same transaction as the link row). The global one is a standing setting of the device; revoking it **does not evict anyone who already joined through it** — those are `usuario_dispositivo` rows, removed with `DELETE /dispositivos/{id}/accesos/{usuario_id}`. Any UI has to say so.
- Emails are lowercased on the way in (both `usuarios` and the invitation) so casing cannot defeat the match on accept. Pre-existing rows were never normalized.
- **Resend is not wired up yet**: creating with an email returns the token but sends nothing; the frontend builds the link for both shapes.

## Database
- Postgres + TimescaleDB. Schema and seed in `db/init.sql` (only applied on a fresh volume) and `db/seed.sql`.
- No migration tool: schema changes go in **two** places — folded into `db/init.sql` for fresh installs, and as a numbered script under `db/migrations/` to apply by hand (`docker compose exec -T timescaledb psql -U postgres -f - < db/migrations/NNN_x.sql`).
- IDs are UUIDs (`gen_random_uuid()`) except `tipos_sensor.id` (SERIAL, small fixed catalog).
- `mediciones.sensor_id` intentionally has no FK constraint — a Timescale recommendation for hypertables at this scale.

## ESP32 firmware (`esp/`)
- `programa_base.ino` is the template with all the common logic (WiFi provisioning, secret in NVS, rotation, sending readings), marked with `// Replace ->`. The sketches under `programas/` are **generated** by `python esp/generar_sketches.py` — never hand-edit them, the next run overwrites the file. Common logic goes in the template; a new order means a new entry in that script's `SKETCHES` dict (device/sensor UUIDs, secret, sensor include/init/read function). `modulos/*.ino` are reference snippets, not compiled.
- **Compile with the `huge_app` partition scheme**: `arduino-cli compile --fqbn esp32:esp32:esp32:PartitionScheme=huge_app esp/programas/<sketch>` (IDE: Tools, Partition Scheme, "Huge APP"). The default splits flash into two ~1.25 MB app partitions for OTA rollback, a feature this project does not use (each order is flashed by hand); `huge_app` gives one 3 MB partition (~38 % used vs ~92 %), which is the real per-order headroom for sensor libraries. NVS sits at the same offset under both, so nothing already flashed is affected. Revisit if OTA ever gets implemented.
- Compile check without hardware: `arduino-cli compile --fqbn esp32:esp32:esp32 esp/programas/<sketch>` (the Arduino IDE ships the binary under `resources/app/lib/backend/resources/`).
- Sends `POST {API_URL}` with `X-Dispositivo-Id` + `Authorization: Bearer <secret>` and a `{"mediciones": [{"sensor_id", "value", "time"}, ...]}` body, matching `schemas/medicion.py`. `time` is ISO-8601 UTC and optional (omitted, the backend stamps arrival time). It reads back `intervalo_sugerido` to adjust its interval at runtime.
- **Readings are buffered, not sent inline.** `leerYBufferizar()` pushes into a static RAM ring buffer and `flushBuffer()` drains it oldest-first in chunks of `MAX_POR_ENVIO`, one chunk per `loop()` pass so the BOOT button stays responsive while draining. The queue only advances on a 2xx; a failed POST is simply retried, which is safe thanks to the unique index. On overflow the oldest entry is overwritten and counted in `descartadasPorOverflow` — fresh data wins. RAM only, on purpose: with no power there is nothing to save, and flushing to NVS every 60 s wears the flash.
- Because of that, `loop()` reads the sensors **before** the WiFi check — the old early `return` meant an outage produced no data at all, not just no upload.
- Each entry stores a `uint8_t` index into `SENSOR_IDS`, not the UUID string (12 B vs ~48 per reading); the generator emits that enum + array per sketch.
- **`CAPACIDAD_BUFFER = 6000` is a linker limit, not a design choice.** The ESP32 reserves a fixed ~124 KB `dram0_0_seg` for globals/statics, and WiFiManager + HTTPClient + ArduinoJson already take ~50 KB of it, so ~6150 entries is roughly the ceiling regardless of the chip's 320 KB of RAM (and independent of the partition scheme). Heap-allocating in `setup()` would lift the cap but moves a compile-time-verified limit to a runtime one (a failed `malloc` has to be handled, and a successful compile no longer proves the buffer fits) — judged not worth it. If a future order needs more autonomy at its interval, that is a trade-off to bring back for a decision, not a number to bump.
- The clock comes from SNTP (`configTime(0, 0, ...)`, UTC) right after the WiFi connects; readings taken before the first sync are buffered with `epoch = 0` and sent without `time`.
- WiFi is **not** hardcoded: the sketches use `WiFiManager` (SoftAP + captive portal). With no saved network the board raises the `SensoresIoT-Setup` AP and the customer loads their WiFi from a phone; credentials persist in flash. Holding BOOT (GPIO0) for 5 s **while the board is already running** wipes them and reopens the portal (`chequearResetWifi` in `loop()`, which is kept free of blocking delays so the press can be timed). It deliberately does not run at startup: GPIO0 is a bootstrap pin, so holding it during reset puts the ESP32 in bootloader mode.
- The secret lives in NVS (`Preferences`, namespace `dispositivo`); `SECRET_DISPOSITIVO_INICIAL` is only the factory value copied there on first boot, and after a rotation the NVS copy is what gets sent. `API_BASE`, `DISPOSITIVO_ID`, the initial secret and the sensor UUIDs are hardcoded per-sketch, one build per order.

## Frontend (`frontend/`) — página de consumo, Tier 5.2

React 19 + Vite + TypeScript + Tailwind v4. Es **sólo la app de cliente** (`app.dominio`); la landing y el panel de admin no arrancaron. Porta un mockup estático ya aprobado y congelado.

- **Comandos** (desde `frontend/`): `npm run dev` (:5173), `npm run build`, `npx tsc --noEmit -p tsconfig.app.json`. Sin tests. `tsconfig.app.json` tiene `strict`, así que los `| null` de `tipos.ts` se verifican de verdad.
- **El proxy de Vite (`/api` -> `:8000`) no es comodidad, es requisito**: la cookie de refresh es `httponly` + `samesite`, no viaja cross-origin. En dev el front tiene que ser same-origin. `VITE_API_URL` lo sobreescribe para otros entornos.
- **Tokens de color en `src/index.css`, dentro de `@theme`** (Tailwind v4 es CSS-first, no hay `tailwind.config.js`); de ahí salen `bg-surface`, `text-text-muted`, `border-border`. El oscuro es el default en `:root`, el claro se reasigna en `[data-theme="light"]` y bajo `prefers-color-scheme`. **Nunca un color literal en un componente** — si falta un tono, agregar el token.
- **`--accent` vs `--accent-strong`**: el primero es el tono claro para texto/íconos/foco, el segundo el relleno sólido con texto blanco encima. No son intercambiables (el claro no llega a 4.5:1 con blanco).
- **Un hue fijo por tipo de sensor** (`utils/sensores.ts`), mapeado por nombre normalizado porque el casing no es confiable (`seed.sql` guarda `temperatura`, el alta por API hace `.capitalize()`). Ninguno usa el hue del chrome, para que el color siga significando algo.
- **`src/tipos.ts` espeja `backend/schemas/`** con los nombres tal cual (español, snake_case). No renombrar al importar: así un cambio de contrato salta en el type-check.
- **`hooks/usarCarga.ts` es el único mecanismo de fetching** (nada de SWR ni TanStack, a propósito). Dos efectos separados: uno carga (se reinicia con la identidad de `cargar` o con `refrescar()`), otro programa el poll, así cambiar la cadencia reprograma el próximo tick sin recargar. `cargar` tiene que venir memoizado.
- **`services/api.ts`** tiene el interceptor de refresh con un solo POST en vuelo compartido: si varias requests expiran juntas esperan el mismo refresh en vez de rotar el token N veces invalidándose entre sí.
- **`components/graficos/Grafico.tsx`** es el elemento distintivo: área degradada sobre Recharts, `dot` fijo al dominio de la ventana. Un hueco corta el trazo en tramos en vez de interpolar — el silencio de un equipo tiene que verse, porque no existe alerta de "dejó de reportar" — y una lectura aislada entre dos huecos se marca con un círculo, porque un tramo de un solo punto no dibuja nada. `utils/series.ts:serieDeGrafico` no recalcula resolución: lee `bucket_seg`/`intervalo_seg` de la respuesta (el paso real usado) y sólo decide dónde va un hueco.
- **El estado de conexión lo resuelve el backend, en una sola función**: `dispositivo_service.esta_online(last_seen_at, intervalo_efectivo_seg)` (`INTERVALOS_DE_GRACIA = 3`), que viaja como `online` en las tres respuestas que muestran equipos (`/estado`, panel, inventario). Antes cada pantalla lo derivaba contra su propio reloj y el mismo equipo se veía distinto en dos lados. El front sólo mapea: `utils/tiempo.ts:estadoDispositivo(lastSeenAt, online)` separa `nunca` de `sin-reportar`.
- **`estadoDispositivo` (el equipo) y `lecturaDesactualizada` (una lectura) son preguntas distintas.** La segunda se sigue derivando en el front con el reloj local porque el backend no expone frescura por sensor; la usan la tarjeta del panel (que apaga sensor por sensor, no el equipo entero) y el detalle de sensor. Comparte los 3 intervalos de gracia con el backend.
- **El límite del plan en el selector de rango se marca, no se bloquea**, y es derivado, no un flag: `utils/retencion.ts` lo saca de `retencion_dias` en la respuesta de `/grafico` (plan del **dueño** del equipo, y el admin exento) porque el catálogo `planes` no tiene columna para esto. `BarraVentana` pinta en violeta las opciones que exceden la retención (`rangoExcedeRetencion`, más `Máx` vía `permiteHistorialCompleto`) pero se eligen igual: el backend recorta subiendo `desde` y responde 200, y `AvisoVentana` dice desde cuándo se está mostrando con link a `/plan`. Bloquearlas dejaba al usuario sin ver nunca su propio límite sobre sus propios datos, e incoherente con el zoom, que siempre pudo producir cualquier ventana.
  - **`AvisoVentana` no confía en el `recortado` del backend a secas**: el piso se calcula con el `now()` del servidor, siempre posterior al del cliente, así que pedir 7 d con 7 d de retención viene marcado como recortado sin que falte un dato — sólo cuenta si movió el borde más que el margen de reloj (`recorteEsMaterial`). Y si el equipo empezó a reportar después del piso del plan, gana el aviso de "primera vez": ahí lo que falta a la izquierda no existe en ninguna suscripción y ofrecer retención extendida sería mentir.
  - `utils/retencion.ts:limiteDeVentana` es el único lugar que resuelve todo esto, y lo consumen las tres piezas que tienen que contestar lo mismo: el `desdeMs` del eje X, la franja violeta del corte (`Grafico:corteDePlanMs`) y el aviso. **El eje arranca en `desde_efectivo`, no en la ventana pedida**: dibujar el rango completo deja el tramo recortado en blanco, indistinguible de un equipo que estuvo mudo, y con 7 días de retención pedir un año dejaría el 98 % del cuadro vacío con las lecturas aplastadas contra el borde derecho.
- **Los hooks del detalle se parten por cadencia, no por pantalla.** `features/dispositivo/usarDispositivo.ts`: `useDispositivo` y `useSensoresConMeta` no pollean (nada de lo que devuelven cambia solo), `useEstadoDispositivo` sí (`last_seen_at`, `online` y alertas disparadas). `usarGraficos.ts` tiene los dos hooks de lecturas. Las dos pantallas de detalle consumen los mismos hooks; la de sensor filtra por `sensorId`. **`useAlertasDispositivo` corre a la cadencia del equipo y no a `pollDeVentana`**: los gráficos dejan de pollear con un rango histórico elegido, pero una alerta se dispara *ahora*.
- **La cadencia del poll la marca el equipo y se deriva en el render (nunca con `useEffect` + `setState`)**: sale de `siguiente_medicion`, así el pedido cae justo después del dato nuevo en vez de a mitad de camino (con 60 s fijos sobre un equipo que reporta en el segundo 41, cada lote llegaría con ~19 s de antigüedad y las series derivarían entre sí sin corregirse). Gráficos y alertas comparten ese número, y compartirlo es lo que los mantiene alineados: los timers vencen juntos y se reprograman juntos con la respuesta que ya dispararon. Que `usarCarga` reinicie su `setTimeout` al cambiar `intervaloMs` no los mata de hambre: el reinicio ocurre una vez por período y después del vencimiento, no en lugar de él.
- **`GET /dispositivos/{id}` trae `limites`: los límites del plan del DUEÑO del equipo** (`puede_alertas`, `max_alertas`, `intervalo_minimo_seg`), resueltos con `plan_service.limites_de_dispositivo`. Existe porque el front sólo conocía el plan de la cuenta propia (`useSesion().plan`) y gateaba cosas del equipo con eso: un free con acceso compartido a un equipo premium veía "Las alertas son premium" mientras el gráfico de esa misma pantalla dibujaba las líneas de umbral de esas reglas. **`useSesion().plan` es el plan de la cuenta y gobierna otra cosa** (compartir los equipos propios); todo lo del equipo sale de `dispositivo.limites`. `retencion_dias` sigue viajando sólo en `/grafico` a propósito: el recorte ya está construido sobre esa respuesta y duplicarlo daría dos fuentes para el mismo límite. La misma respuesta trae `notificar`, que no es un límite sino la preferencia de quien consulta (`null` = admin sin vínculo).
- **El gate de edición de alertas en la UI espeja `ROLES_EDICION`** vía `utils/dispositivos.ts:puedeEditar(dispositivo.rol)`. No es control de acceso — el backend ya devuelve 403 a un viewer — es no ofrecerle un botón que va a fallar.
- **Silenciar es del equipo y vive sólo en Ajustes**: `ajustes/SeccionNotificaciones.tsx` es un `Segmentado` (Activadas/Silenciadas) sobre `dispositivo.notificar`, con guardado inmediato y optimista (un control de dos estados no necesita botón Guardar, igual que el tema en `cuenta/Ajustes.tsx`). Habilitado para todos los roles a propósito, viewer incluido: es el opt-out de mails de cada uno, no una edición del equipo. Si `notificar` viene `null` la sección no se renderiza.
- El drawer mobile usa `inert` en los dos sentidos (sidebar cerrada / fondo cuando está abierta) en vez de un focus trap a mano.
- **Estructura**: `components/{ui,layout,graficos}` (presentación reutilizable), `features/*` (una carpeta por pantalla con sus hooks al lado), `hooks/` (transversales: `usarCarga`, `usarAhora`, `usarTema`, `usarMedios`, `usarTitulo`, `usarFormulario`), `services/` (`api.ts` cliente + errores, `consultas.ts` endpoints), `utils/` (puras) y `src/tipos.ts`. La regla: si para entender una pantalla hay que saltar entre capas, la capa sobra.
- **Estado actual**: auth, panel, inventario, detalle de equipo y de sensor, historial, alertas, export, intervalo y ajustes (identificación, muestreo, notificaciones, accesos e invitaciones) funcionando. `Alertas` (log global), `PlanPagina` y la edición de perfil (`Cuenta`) son `<Pendiente/>`.

## Roadmap priorizado

### Tier 3 — Bloqueante antes de vender a clientes reales

No hay producción en volumen: cada pedido lleva una combinación de sensores distinta (librerías distintas) y el firmware se compila a mano por pedido. Por eso se descartó el `claim_code` con firmware idéntico — resolvía un problema de escala que hoy no existe. Si alguna vez se fabrica en volumen con firmware único, retomarlo junto con auto-detección de sensores por dirección I2C.

**3.1 — Provisioning de WiFi** ✅ implementado: SoftAP + portal cautivo (`WiFiManager`). SoftAP sobre BLE por compatibilidad — Web Bluetooth no anda en iOS Safari.

**3.2 — Secret del dispositivo: alta y rotación** ✅ implementado.
- *Alta (se mantiene así)*: al crear un pedido se generan a mano en la DB el `dispositivo` y sus `sensores`. Devuelve `dispositivo_id` (no sensible) y `secret` en texto plano; ambos se hardcodean en el `.ino` y se compilan junto con las librerías de ese pedido. El backend guarda sólo el hash SHA256. Aceptable porque no hay volumen: no hace falta desacoplar el secret del compile-time.
- *Rotación*: device-initiated, coherente con que el ESP32 siempre inicia la conexión y nunca escucha (ver "Auth model"). El endpoint manual queda para banco de pruebas/fábrica.
- **Pendiente, bloqueante antes de la primera tanda real**: **flash encryption del ESP32**. Hoy se desconoce si está habilitada (por default viene deshabilitada). Es configuración por software pero graba la clave en eFuses: **irreversible y de una sola vez** por unidad, no se puede activar retroactivamente en equipos ya entregados. Sin eso el secret hardcodeado en el binario es extraíble por cualquiera con acceso físico (dump de flash por USB/serial), tenga rotación o no. Verificar y decidir antes de que salga la primera unidad a un cliente real, no antes de seguir desarrollando.

### Tier 4 — Monetización

**4.1 — Modelo de planes + integración de pago.** Modelo de datos ✅ (`db/migrations/003_planes_suscripciones.sql`, ver "Planes y suscripciones"); **falta el cobro**. Ninguna feature premium se puede gatear sin el concepto de plan/suscripción, por eso va antes que cada feature puntual. Medio de pago: **Mercado Pago**, no Stripe (no soporta cuentas argentinas y el público es sólo Argentina). Para recurrentes en ARS la API es `preapproval`, que notifica cada cobro autorizado por webhook; los webhooks se reintentan y pueden llegar duplicados o fuera de orden, así que el alta tiene que ser idempotente.

**4.2 — Export CSV** ✅ implementado. No es premium: lo único que lo limita es la misma ventana de retención que recorta `/grafico` y `/historial` (free 7 días, premium todo). Exporta el equipo completo (sensores pivoteados), por default el historial entero sin agregar. XLSX pendiente hasta que alguien lo pida — no suma dependencias mientras tanto.

**4.3 — Alertas (premium)** ✅ implementado. Push/SMS más adelante con otro proveedor. **Pendiente, no bloqueante**: la alerta de "dejó de reportar" quedó fuera — es la única que no se puede evaluar inline (se dispara por la *ausencia* de un POST) y necesita un job periódico. Retomar como 4.3.b si aparece demanda.

**4.4 — Multi-usuario (viewer/editor)** ✅ implementado: roles resueltos por el trío `validar_*`, invitaciones por link global o email, y `GET/PATCH/DELETE /dispositivos/{id}/accesos` para listar, cambiar rol y quitar acceso. *Pendiente*: el mail de invitación por Resend. No bloqueante — el front arma el link para las dos formas.

**4.5 — Chat de IA — en duda, no priorizar sin validación.** Es la feature más cara de forma recurrente (tokens por request) y la más difícil de hacer bien (dar contexto real de mediciones sin alucinar, manejar rangos de fechas). No está claro qué dolor resuelve para quien compra un sensor ambiental y típicamente quiere ver un gráfico y recibir alertas. Fuera del roadmap cercano salvo demanda concreta de usuarios reales con un caso de uso específico.
